## 오늘 한 일

### 왜 했나

- 지금은 답을 브라우저 내장 음성으로 읽습니다. 목소리가 기기마다 다르고 듣기에 어색합니다.
- 목소리는 팀이 고르기로 했습니다. 그래서 어떤 목소리를 고르든 끼울 수 있는 경로를 먼저 만들었습니다.

### 백엔드

- 새 경로 `GET/POST /api/pc-consult/sessions/{session_id}/speech` (`backend/app/api/voice.py`). 상담 API 파일은 고치지 않았습니다.
  - GET 은 서버 음성을 쓸 수 있는지와 부품 이름 읽는 법을 돌려줍니다.
  - POST 는 문장 하나를 WAV 로 돌려줍니다.
- 공급자는 `BUILDWISE_TTS_PROVIDER` 로 고릅니다.
  - `none`(기본): 지금처럼 브라우저 음성으로 읽습니다.
  - `openai`: `gpt-4o-mini-tts` 를 씁니다.
  - `http`: 런팟 등에 직접 띄운 공개 모델 서버를 씁니다. `POST {URL}/speech` 가 WAV 를 돌려주면 됩니다.
- 공급자 응답을 끝까지 받은 것만 돌려줍니다. 길이가 모자라거나 전송이 끊긴 것은 실패로 보고, 프론트가 브라우저 음성으로 읽습니다. 공급자가 정상 종료로 보낸 음성이 문장 끝까지인지는 서버가 알 수 없습니다.
- 요청 하나의 전체 시간은 25초까지입니다. 조금씩 오는 응답이 합성 자리를 오래 잡지 않게 했습니다.
- 비용 상한
  - 세션 쿠키로 확인하고, 합성할 수 있는 글자를 그 세션이 받은 답 글자 수의 3배로 묶었습니다.
  - 답을 아직 못 받은 세션은 즉시 반응 4종만 읽을 수 있습니다. 즉시 반응은 서버 캐시에 한 번 만들어 두고 다시 씁니다.
  - 하루·누적 글자 상한을 SQLite 원장에 예약합니다. 합성 자리를 잡은 뒤, 공급자를 부르기 전에 예약합니다. 서버를 다시 켜도 남습니다. 기본은 하루 30,000자, 누적 250,000자입니다.
  - 요청이 몰려 합성 자리를 못 잡은 경우(503)는 예산을 쓰지 않습니다.
- 같은 문장은 캐시에서 줍니다. 즉시 반응("네, 잠시만요.")은 한 번 만들면 다시 만들지 않습니다.
- 부품 이름 읽는 법은 `backend/app/domains/hardware/pc_consultation/reading.py` 에 두었습니다. 70개입니다.
- 계약 파일(`contracts/pc-consult.openapi.json`, `frontend/src/api/pcSchema.d.ts`)을 다시 만들었습니다. 기존 경로는 그대로입니다.

### 프론트

- `serverSpeech.ts`: 서버 음성을 Web Audio 로 재생합니다.
  - 받기와 디코딩을 합쳐 4초 안에 못 끝내거나, 오디오를 깨우지 못하면 그 문장은 브라우저 음성으로 읽습니다.
  - 재생 중에 소리가 멈추면 그 문장을 처음부터 브라우저 음성으로 다시 읽습니다. 잘린 채 다음 문장으로 넘어가지 않습니다.
  - 서버가 2번 연달아 실패하면 60초 동안 브라우저 음성만 씁니다. 429 를 받으면 Retry-After 만큼 쉽니다.
- 답이 오면 첫 두 문장을 바로 받기 시작하고, 문장을 읽는 동안 다음 문장을 미리 받습니다.
- `speechText.ts`: 읽기 직전에만 글을 말로 바꿉니다. 화면 글은 그대로입니다.

  | Ryzen 7 9800X3D       | 라이젠 세븐 구팔공공 엑스쓰리디    |

- 실제 상담 세션에서만 서버 음성을 씁니다. 주소에 `?tts=browser` 를 붙이면 브라우저 음성으로 읽습니다.
- 음성 처리 안내에 두 가지를 적었습니다. AI 가 만든 목소리라는 점, 서버 음성이 켜져 있으면 답 글을 합성 서비스로 보낸다는 점입니다.
- 턴 시간 기록(`?voice-debug`)에 서버·브라우저로 읽은 문장 수와 서버 음성 받기 시간을 더했습니다.

## 결과와 한계

- 확인한 것
  - 백엔드: 새 시험 26건 통과, 전체 315건 통과.
  - 프론트: typecheck, lint, vitest 35파일 408건, build 통과.
  - e2e `voice-lab.spec.ts` 13건(서버 음성 5건 추가)을 3번씩 돌려 39/39 통과. Chrome 헤드리스이고 서버는 흉내만 냈습니다.
    - 그 전에 5번씩 돌린 65회 중 1회는 원래 있던 시험("빠른 답에는…")이 실패했습니다. 문장 사이가 3.6초씩 멈춘 경우였고, 평소에는 30~40ms 입니다.
    - 노트북 메모리가 거의 찬 상태(남은 메모리 0.9GB)라 그 영향으로 보이지만, 확정하지는 못했습니다.
  - 실제 백엔드를 `openai` 공급자로 띄워 경로를 확인했습니다.
    - "네, 잠시만요." 첫 합성 1.75초, 같은 문장 다시는 0.01초(캐시)
    - 세션 한도를 넘으면 429
    - 쿠키 없는 요청은 404
- 실측: `gpt-4o-mini-tts` 로 상담 문장 10개를 합성했습니다. 한 문장을 다 받는 데 1.3~2.9초, 가운데값 2.0초입니다.
  - 다음 문장은 앞 문장을 읽는 동안 받으므로 기다림이 거의 없습니다.
  - 답의 첫 문장은 약 2초를 더 기다립니다. 그 사이는 즉시 반응이 채웁니다. 스트리밍(12/5~6)에서 줄일 예정입니다.
- 안 한 것: 실제 상담 서버에 붙여 듣기, 실제 마이크·스피커 확인, 런팟 공개 모델 서버.
- 알려진 문제
  - `tests/unit/contracts` 의 API 동기화 검사 1건이 실패합니다. dev 에서도 같은 12개 경로로 실패하고, 이번 변경과는 무관합니다(`PREFIX` 로 묶은 상담 경로를 정적 검사가 못 읽음).
  - `pcConsult.css` prettier 경고 1건도 dev 에서부터 있던 것입니다.

## 팀에 부탁할 것

1. 새 API 경로 1개와 환경변수(`BUILDWISE_TTS_*`)를 더했습니다. 공통 계약 절차대로 확인 부탁드립니다. 기본값이 꺼짐이라 설정하지 않으면 동작은 그대로입니다.
2. 목소리 고르기. 후보는 Qwen3-TTS, Fun-CosyVoice3, MOSS-TTS 입니다. 셋 다 한국어를 지원하고 Apache-2.0 이며, 데모로 들어 볼 수 있습니다. OpenAI 기본 목소리로 갈지도 같이 정하면 됩니다.
3. 공개 배포에서 서버 음성을 켤지. 켜면 답 글이 합성 서비스로 나가고, 하루 상한 안에서 캠프 예산을 씁니다.
