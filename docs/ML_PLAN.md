# ML 계획 — 상담 발화 의도 분류 + 조건(슬롯) 추출 (3주차)

3주차 ML/DL 산출물은 **상담 발화 이해(NLU)** 모델입니다. 고객이 채팅에 쓴 한 문장에서
① 무엇을 원하는지(의도)와 ② 상담에 필요한 조건(슬롯: 예산 · 용도 · 모델 크기 …)을 뽑습니다.

지금(2026-11-12)은 **규칙 기반 기준선**과 **평가셋 · 평가 스크립트**가 있습니다.
3주차 학습 모델은 같은 인터페이스를 구현해 갈아 끼우고, 같은 평가셋 · 같은 지표로 기준선과 비교합니다.

## 1. 지금 있는 것

| 무엇 | 위치 |
|---|---|
| 인터페이스 `IntentClassifier` · `SlotExtractor` · `NluPipeline` | `backend/app/nlu/base.py` |
| 규칙 의도 분류기(공통 엔진 — 낱말 가중치 합) | `backend/app/nlu/rules.py` |
| 하드웨어 상담 규칙(의도 낱말표 · 슬롯 정규식) | `backend/app/domains/hardware/nlu.py` |
| 지표(의도 정확도 · macro-F1, 슬롯 micro F1) | `backend/app/nlu/metrics.py` |
| 평가 스크립트 | `backend/app/nlu/evaluate.py` — `uv run python -m app.nlu.evaluate [--errors] [--json 결과.json]` |
| 평가셋 v1 (가상 발화 72건) | `data/nlu/hardware_eval_v1.jsonl` |
| 테스트(지표 · 평가셋 형식 · 기준선 하한) | `backend/tests/test_nlu.py` |

결과 형식: `{"intent", "confidence", "slots", "source"}` — 규칙은 `source="rules"`, 학습 모델은 `"model"` 로 적습니다.
채팅 API(`POST /api/sessions/{id}/messages`)가 고객 메시지마다 이 결과를 `chat_messages.nlu` 에 저장합니다.
외부 LLM 은 부르지 않습니다(Mock 모드).

## 2. 라벨 기준

### 의도 (6개, 한 발화에 하나)

| 의도 | 뜻 | 경계 사례 |
|---|---|---|
| `new_recommendation` | 새 장비(완제품 · 부품) 추천 · 구매 상담 | "어떤 장비를 사야 할까요?" 처럼 사려는 뜻이면 여기 |
| `upgrade_diagnosis` | **가진 장비**로 되는지 · 업그레이드하면 되는지 | "램 8기가 노트북으로 7B 돌아갈까요?" — 지금 가진 장비 이야기면 여기 |
| `compatibility_question` | 부품 · 장비끼리 맞는지(파워 · 케이스 · 슬롯 · 규격 · 연결) | 사려는 부품이 내 장비에 맞는지 묻는 것도 여기 |
| `quote_request` | 견적 · 총액 · 할인 · 주문 · 견적서 출력 | "이 노트북이랑 모니터 같이 사면 할인돼요?" 는 견적 |
| `cloud_comparison` | 클라우드 GPU 를 빌리는 것과 사는 것 비교 · 클라우드 비용 | 클라우드 말이 없어도 "그래도 장비를 사는 게 나을까요?" 처럼 대여와 비교하는 뜻이면 여기 |
| `other` | 그 밖(인사 · 감사 · 배송 · 환불 · 매장 · 용어 질문 등) | 장비 상담과 관계없는 말 |

### 슬롯 (9개, 값은 아래처럼 정규화)

| 슬롯 | 값 | 기준 |
|---|---|---|
| `budget_max` | 원(정수) | 구매 예산 · 상한. 범위면 큰 값("100만~150만" → 1,500,000). 시간당 가격 · 월 클라우드 지출은 예산이 아님 |
| `purpose` | `llm_finetune` · `llm_inference` · `image_generation` · `dl_study` · `general_dev` | 파인튜닝 · LoRA → finetune / AI 모델 실행 · 추론 → inference / 이미지 생성 / 공부 · 수업 · 입문 · 과제 / 코딩 · 개발 |
| `model_params_b` | 10억 단위 수 | "7B" → 7, "70억 파라미터" → 7 |
| `precision` | `fp32` · `fp16` · `int8` · `int4` | 4비트 · QLoRA · GPTQ · AWQ → int4, 비트를 말하지 않은 "양자화" → int4, 여러 개면 마지막에 말한 것 |
| `product_types` | `laptop` · `desktop` · `gpu` · `server` · `monitor` (여러 개) | **사려는 · 물어보는** 장비만. "PC" → desktop, "GPU 서버" → server. 클라우드 GPU 는 상품 유형이 아님 |
| `owned_device` | `laptop` · `desktop` | **가진** 장비("제 노트북", "지금 쓰는 PC", 업그레이드 대상) |
| `owned_ram_gb` · `owned_vram_gb` | GB(정수) | 가진 장비의 램 · 그래픽 메모리. 내장 그래픽 → 0. 원하는 사양("램 32GB 이상")은 슬롯이 아님 |
| `weekly_hours` | 주당 시간 | "하루 3시간" → 21, "한 달 40시간" → 40 × 12 ÷ 52 = 9.2(소수 첫째 자리) |

- 발화는 모두 **가상**으로 씁니다. 실존 인물 · 연락처 · 실제 상품명 · 실제 서비스 이름을 넣지 않습니다(테스트가 연락처 모양을 검사).
- 애매하면 라벨을 정하기 전에 이 표에 경계 사례를 한 줄 더하고, 같은 기준으로 다시 라벨합니다.

## 3. 데이터 수집 · 분할 계획

| 단계 | 내용 | 목표 |
|---|---|---|
| 평가셋 v1 (완료) | 의도별 12건 = 72건, 라벨 기준 위 표 | **test 전용으로 고정** — 학습 · 규칙 수정에 쓰지 않음 |
| 학습 데이터 | 팀원 5명이 의도별로 가상 발화 작성(서로 다른 말투 · 길이 · 오타), 한 사람이 쓴 원문을 다른 사람이 라벨 → 불일치는 회의로 기준 보강 | 의도별 100건 이상(600건+) |
| 바꿔 쓰기(증강) | 원문 하나에서 숫자 · 장비 · 어순을 바꾼 변형 2~3개 | 같은 원문에서 나온 변형은 **같은 분할**에 둠(누수 방지) |
| 실제 채팅 로그 | 시연 · 사용자 테스트에서 동의를 받은 대화만, 개인정보 지운 뒤 | 확장(동의 기반) |

- 분할: train 70% · dev 15% · test 15%, 의도 비율을 맞춰(층화) 나눕니다. 평가셋 v1 은 별도 test 로 따로 보고합니다.
- 라벨 일치도: 두 사람이 같은 100건을 따로 라벨해 의도 일치율을 적습니다(낮으면 기준을 다시 씀).

**읽는 법 · 한계**
- 규칙은 평가셋을 쓰기 **전에** 작성했고, 측정한 뒤 평가셋에 맞춰 규칙을 고치지 않았습니다(1회 측정). 다만 평가셋과 규칙을 같은 사람이 썼으므로 실제 고객 발화에서는 더 낮을 수 있습니다.
- 72건은 작습니다. 의도별 12건이라 한 건이 F1 을 0.04~0.08 움직입니다.
- 많이 틀린 유형: 낱말표에 없는 구매 표현("사야 하나요", "PC 맞추고", "있을까요?") → `other` 로 빠짐 /
  보유 단서 없이 장비를 말하는 진단 발화("램 8기가 노트북으로") → 가진 장비를 사려는 장비로 봄 /
  "GPU 서버" 를 gpu + server 로 둘 다 뽑음 / 클라우드 문장 안의 "그래픽카드" 를 놓침.
  → 학습 모델이 이기기를 기대하는 지점입니다. 오류 목록은 `--errors` 로 봅니다.
- `tests/test_nlu.py` 는 기준선이 의도 정확도 · macro-F1 · 슬롯 F1 **0.85** 아래로 떨어지면 실패합니다(회귀 방지 하한).

## 6. 학습 후보 모델

| 후보 | 의도 | 슬롯 | 메모 |
|---|---|---|---|
| A. TF-IDF(글자 n-gram) + 로지스틱 회귀 | ✅ | — (규칙 유지) | 가장 빠른 학습 기준선. 몇 분이면 학습 |
| B. 한국어 사전학습 인코더(BERT · RoBERTa · ELECTRA 계열) 미세조정 | ✅ 문장 분류 | ✅ 토큰 분류(BIO) | 의도 + 슬롯 공동 학습(Joint) 구조. 공개 체크포인트는 라이선스를 확인하고 고름 |
| C. B 의 슬롯 구간 + 규칙 정규화 | — | ✅ | 모델은 "어디가 예산인지" 구간만, 숫자 바꾸기("2천만" → 20,000,000)는 지금 규칙 함수를 재사용 |

- 학습 환경 · GPU 비용은 팀이 정합니다(도구 API `POST /api/tools/vram-estimate` 로 필요 VRAM 을 미리 볼 수 있음).
- 프롬프트로 LLM 에 맡기는 방식은 3주차 범위 밖입니다(실제 LLM 연결은 확장).

## 7. 갈아 끼우는 방법

1. `IntentClassifier` · `SlotExtractor` 를 구현한 클래스를 만듭니다(`source = "model"`, `classify(text)` · `extract(text)`).
2. `backend/app/domains/hardware/nlu.py` 의 `build_nlu()` 가 그 클래스를 쓰게 바꿉니다
   (확신도가 낮으면 규칙 결과로 대체하는 방식도 같은 자리에서).
3. `uv run python -m app.nlu.evaluate --json 모델결과.json` 으로 같은 평가셋 점수를 냅니다 → 위 5번 표와 나란히 적습니다.
4. 채팅 · API · 화면은 고치지 않습니다(결과 형식이 같음). 모델 파일은 저장소에 커밋하지 않고 받는 방법만 문서에 적습니다.

## 8. 3주차 결과서 목차(안)

1. 문제 정의 — 왜 의도 · 슬롯인가(채팅 상담이 업무팀 실행으로 이어지는 구조)
2. 데이터 — 출처(가상 · 동의 기반) · 라벨 기준(2번 표) · 분할 · 통계(의도별 건수, 슬롯 분포) · 라벨 일치도
3. 기준선 — 규칙 방식과 점수(5번 표)
4. 모델 — 구조 · 입력 처리 · 하이퍼파라미터 · 학습 환경 · 학습 시간
5. 평가 — 지표 표(기준선 대비) · 혼동행렬 · 슬롯별 F1 · 오류 사례 분석
6. 서비스 적용 — 인터페이스 교체, 응답 시간, 확신도 낮을 때 대체 동작
7. 한계와 다음 단계 — 데이터 규모, 실제 고객 발화, 음성 입력(확장)

## 9. 범위 밖 (확장)

- **음성 상담(STT)** — 받아쓴 문장을 같은 NLU 에 넣는 구조로 붙일 수 있습니다. 지금은 구현하지 않습니다.
- **실제 LLM** — 되묻는 문장 · 비교 설명 생성. 지금은 규칙 문장(Mock).
- **상담 결과 이메일 · 공유 링크** — 개인정보를 다루므로 고객 동의 기반으로 따로 설계합니다. 지금은 구현하지 않습니다.
